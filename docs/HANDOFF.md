## 2026-09-13 — MSIX Store package now builds successfully via manual MakeAppx packaging

**Resolved: the automated MSBuild single-project MSIX pipeline (`GenerateAppxPackageOnBuild`/`PublishAppxPackage`) never reliably invokes actual packaging on this project/SDK combination**, despite trying every documented property combination (`-p:Platform=x64`, `PublishProfile`, `PublishAppxPackage=true`, invoking `PrepareForRun`/`Publish` targets directly). `GenerateMsixPackage`/`GenerateUploadMsixPackage` simply never get scheduled — root cause not fully proven (suspected .NET SDK outer/inner build interaction), not worth more time chasing.

**The fix: bypass that pipeline entirely.** [Build-StorePackage.ps1](../Build-StorePackage.ps1) (repo root) is the one command for producing a Store-ready package:
1. Stops any running `EliteFIPServer.exe` (would lock output files).
2. `dotnet publish EliteFIPServer.UI.csproj -c Release -p:BuildAsMsix=true -p:Platform=x64` — compiles and copies content (Images, wwwroot, NLog.config) into `EliteFIPServer.UI\bin\x64\Release\net10.0-windows10.0.19041.0\win-x64\`. Deletes the nested `publish\` subfolder `dotnet publish` also creates there (a separate, incomplete deployment layout that must not be included in the package).
3. Runs `Generate-StoreManifest.ps1` to write a real, identity-merged `AppxManifest.xml` directly into that same output folder.
4. Runs `makeappx.exe pack /d <that folder> /p artifacts\msix\EliteFIPServer.msix /o` (auto-locates the newest `Microsoft.Windows.SDK.BuildTools` in the NuGet cache).

Two environment/tooling bugs had to be fixed before this worked, both unrelated to the pipeline problem above:
- `WinAppSdkValidateAppxManifestItems` (old `microsoft.windows.sdk.buildtools.msix` 1.7.251221100) failed loading `System.Security.Permissions` under .NET 10 SDK — fixed via a `FixWinAppSdkMsixTaskAssemblyLoad` target in the csproj that copies that assembly from the (also-pinned) `System.Security.Permissions` NuGet package into the SDK task's own folder before it loads. A project `PackageReference` alone can't fix this — MSBuild loads SDK-provided tasks independently of the consuming project's dependency graph.
- The old `Microsoft.Windows.SDK.BuildTools` (10.0.26100.4654) ships a stale manifest schema that wrongly rejects package identity names starting with an uppercase letter (confirmed against Microsoft's current docs — `[A-Za-z]` is valid, not just `[a-z]`). Fixed by pinning `Microsoft.Windows.SDK.BuildTools` to `10.0.28000.2705`. Both pins in `EliteFIPServer.UI.csproj` are **unconditional** (not gated on `BuildAsMsix`) — a `Condition="'$(BuildAsMsix)' == 'true'"` on these specific `PackageReference` items was silently ignored during `dotnet restore` (restore-time evaluation doesn't reliably honor it), so the old transitive versions kept winning until the condition was removed.

**Also found and fixed a real bug in [Generate-StoreManifest.ps1](../Generate-StoreManifest.ps1) itself:** `[regex]::Replace($str, $pattern, $replacementString, 1)` does not mean "replace first match only" — there is no such static overload, so PowerShell resolved the trailing `1` to `RegexOptions.IgnoreCase` on the 3-arg-plus-options overload, which replaces **all** matches. Since `Name="..."` appears on `<Identity>`, `<TargetDeviceFamily>`, and the `runFullTrust` `<Capability>`, every manifest generated before this fix had the latter two silently overwritten with the Store identity name — `TargetDeviceFamily` broken and `runFullTrust` missing entirely. Fixed by scoping the Name/Publisher substitution to just the `<Identity>` block via a MatchEvaluator. **Verify this specifically if anything regresses**: check `AppxManifest.xml` inside a built `.msix` has `TargetDeviceFamily Name="Windows.Desktop"` and `rescap:Capability Name="runFullTrust"` intact, not the package identity name.

The script also substitutes `$targetnametoken$.exe` → `EliteFIPServer.exe` and `$targetentrypoint$` → `Windows.FullTrustApplication` (the standard EntryPoint sentinel for a converted full-trust Win32 app) — these are normally filled in by the automated pipeline we're bypassing, so manual packaging must do it instead.

Package is intentionally unsigned (`AppxPackageSigningEnabled=false`) — Partner Center re-signs on submission. Local sideload/signing was considered and declined (a self-signed cert wouldn't be trusted by Windows for install anyway without extra steps) — verification will happen via actual Store upload.

The bundled Playwright Chromium works fine once pinned explicitly. Changing `.mcp.json` requires an MCP reconnect (VS Code restart worked; a lighter reload may also work but is untested).
- **Panel server autostart:** `AutostartPanelServer` is a persisted user setting (Settings → "Start Panel Server automatically", off by default in a fresh profile). A running `EliteFIPServer.exe` with port 4545 not listening is expected, not a bug, until that toggle (or a manual start) is used.
- **New agent added:** `.claude/agents/elite-build-runner.md` — runs the stop/test/build/restart lifecycle and reports back only totals/PID/URL, keeping raw MSBuild/signing/test output out of the main conversation. The real Partner Center identity now lives only in `EliteFIPServer.UI/StoreIdentity.local.json` (gitignored, machine-local; a tracked `.template` sibling shows the shape). A normal Debug build is completely unaffected (validated: 25/25 tests, clean build).
