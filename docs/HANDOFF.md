## 2026-09-13 — MSIX Store package: automated pipeline abandoned, manual MakeAppx packaging works, one real post-merge regression fixed

**`EliteFIPServer.UI.csproj` never opts into MSBuild's Appx packaging pipeline at all — this is deliberate and final.** Earlier attempts wired up `WindowsPackageType=MSIX`/`EnableMsixTooling`/`GenerateAppxPackageOnBuild`/`PublishAppxPackage`/a `PublishProfile`, tried every documented CLI property combination, and even invoking `PrepareForRun`/`Publish` targets directly — `GenerateMsixPackage`/`GenerateUploadMsixPackage` simply never got scheduled on this project/SDK combination (root cause never proven; suspected .NET SDK outer/inner build interaction). Worse, two packages added only to satisfy that pipeline's validation step (`Microsoft.Windows.SDK.BuildTools.MSIX`, `System.Security.Permissions`, both `ExcludeAssets="all"`) turned out to still shift NuGet's transitive dependency resolution enough to **crash `EliteFIPServer.exe` at startup inside `Microsoft.UI.Xaml.dll`** — confirmed by git-bisecting the csproj (swap in the pre-`StorePrep` version → crash gone; re-add pieces → crash reproduces with just those two `PackageReference` items). Given the automated pipeline never worked anyway, the fix was to remove all of it: `WindowsPackageType` is unconditionally `None`, `WindowsAppSDKSelfContained` is unconditionally `true` (self-contained WinAppSDK deployment — no Windows App Runtime install dependency for end users; .NET itself is **not** bundled, so users need the .NET 10 and ASP.NET Core 10 runtimes, as stated on the Store listing), and `Package.appxmanifest`/`Images\*.png` remain in the project only as plain `None`/`Content` items for the manual packaging script (below) to read from the build output — MSBuild's own Appx machinery is never invoked.

**Producing a Store-ready package: [Build-StorePackage.ps1](../Build-StorePackage.ps1)** (repo root), one command, no special MSBuild properties needed:
1. Stops any running `EliteFIPServer.exe` (would lock output files).
2. `dotnet publish EliteFIPServer.UI.csproj -c Release -p:Platform=x64` — a normal framework-dependent publish (only the Windows App SDK is bundled); Images/wwwroot/NLog.config land in `EliteFIPServer.UI\bin\x64\Release\net10.0-windows10.0.19041.0\win-x64\` via their existing `Content`/`CopyToOutputDirectory` items. Deletes the nested `publish\` subfolder `dotnet publish` also creates there (a separate, incomplete deployment layout that must not be included in the package payload).
3. Runs `Generate-StoreManifest.ps1` to write a real, identity-merged `AppxManifest.xml` directly into that output folder — merges `EliteFIPServer.UI/StoreIdentity.local.json` (gitignored, real Partner Center values) and the current version from `EliteFIPServer.Version.props` into the tracked `Package.appxmanifest` template (which keeps permanent placeholder `Identity`/`PublisherDisplayName` values and is never itself modified). Also substitutes `$targetnametoken$.exe` → `EliteFIPServer.exe` and `$targetentrypoint$` → `Windows.FullTrustApplication` (the standard EntryPoint sentinel for a converted full-trust Win32 app) — both normally filled in by the automated pipeline we're not using.
4. Restores `tools\StoreBuildTools\StoreBuildTools.csproj` — an isolated, App-project-independent pin of `Microsoft.Windows.SDK.BuildTools` `10.0.28000.2705` (needed only to work around a stale `MakeAppx.exe` manifest-schema check in the older transitive `10.0.26100.4654`, which wrongly rejects package identity names starting with an uppercase letter — confirmed wrong against Microsoft's current docs, `[A-Za-z]` is valid). Kept isolated in its own throwaway project specifically so it can never again affect `EliteFIPServer.UI.csproj`'s own dependency graph, per the incident below.
5. Runs `makeappx.exe pack /d <output folder> /p artifacts\msix\EliteFIPServer.msix /o` (auto-locates the newest `Microsoft.Windows.SDK.BuildTools` version in the NuGet cache).

Package is intentionally unsigned — Partner Center re-signs on submission. Local sideload/signing was considered and declined (a self-signed cert wouldn't be trusted by Windows for install anyway without extra steps) — verification will happen via actual Store upload. Verified end-to-end: `artifacts\msix\EliteFIPServer.msix` builds successfully; its embedded manifest correctly has the real identity, `TargetDeviceFamily Name="Windows.Desktop"`, and `rescap:Capability Name="runFullTrust"` intact.

**Incident — 2026-09-13, post-`StorePrep`-merge crash (now fully resolved, see above):** immediately after merging `StorePrep` into `main`, `EliteFIPServer.exe` crashed on every launch, even for a plain non-MSIX Debug build. Investigation went through two false leads before the real cause: (1) first suspected a `Microsoft.Windows.SDK.BuildTools` `10.0.28000.2705` pin directly in `EliteFIPServer.UI.csproj` (a PRI-resource-format mismatch theory) — reverting it and rebuilding **still crashed** (fault moved from `combase.dll` to `Microsoft.UI.Xaml.dll`, same `0xC000027B` exception family), ruling that out; (2) then suspected stale incremental `bin`/`obj` state from heavy `-p:Platform=x64`/`-p:BuildAsMsix=true` experimentation — a full clean rebuild made the crash disappear once, but it **reproduced again** on the next `dotnet publish -p:BuildAsMsix=true` + rebuild cycle, disproving that theory too. The actual cause, found by bisecting the csproj against the pre-merge commit: the two unconditional `Microsoft.Windows.SDK.BuildTools.MSIX`/`System.Security.Permissions` `PackageReference` items (added to work around the automated pipeline's validation crash) were shifting transitive dependency resolution project-wide even with `ExcludeAssets="all"` — that attribute stops a package's *own* assets from flowing into the project, but does not exempt it from participating in NuGet's version-conflict resolution for shared transitive dependencies. **Lesson: `ExcludeAssets="all"` is not isolation from a `PackageReference`'s effect on the overall dependency graph — for a package added only to satisfy an unrelated tool, prefer restoring it in a genuinely separate project (see `tools/StoreBuildTools/`) over adding it to the app project at all, regardless of asset exclusion.** Given the automated pipeline these packages existed to serve never worked anyway, the actual fix was removing the pipeline (and both packages) entirely, as described above — resolved and independently re-validated (25/25 tests, clean build, process confirmed alive 9+ seconds after launch, both Debug/AnyCPU and Release/x64).

**Also found and fixed a real bug in [Generate-StoreManifest.ps1](../Generate-StoreManifest.ps1) itself, unrelated to the above:** `[regex]::Replace($str, $pattern, $replacementString, 1)` does not mean "replace first match only" — there is no such static overload, so PowerShell resolved the trailing `1` to `RegexOptions.IgnoreCase` on the 3-arg-plus-options overload, which replaces **all** matches. Since `Name="..."` appears on `<Identity>`, `<TargetDeviceFamily>`, and the `runFullTrust` `<Capability>`, every manifest generated before this fix had the latter two silently overwritten with the Store identity name — `TargetDeviceFamily` broken and `runFullTrust` missing entirely. Fixed by scoping the Name/Publisher substitution to just the `<Identity>` block via a MatchEvaluator. **Verify this specifically if anything regresses**: check a built `.msix`'s `AppxManifest.xml` has `TargetDeviceFamily Name="Windows.Desktop"` and `rescap:Capability Name="runFullTrust"` intact, not the package identity name.

## 2026-09-30 — Release tags, Matric DLL removed, first public push

- **Release tags:** each Store build gets a lightweight `vX.Y.Z` tag, and a lightweight `Release` tag moves to the newest one (`git show Release:EliteFIPServer.Version.props` gives the last Store version; 4.0.51.0 at this point). `/elite-release` does the commit, tags and release notes; moving `Release` on the remote needs `git push -f origin Release`.
- **MatricIntegration.dll** (Ex Machina's proprietary library) was removed from the repository and purged from history before the public push. Builds find it via [EliteFIPServer.Matric.props](../EliteFIPServer.Matric.props): `-p:MatricIntegrationPath`, then a gitignored `libs\Matric\` copy, then the installed Matric Desktop folder. At runtime `MatricAssemblyResolver`/`MatricLocator` load it from the user's Matric install. Because history was rewritten, commit hashes from before 2026-09-30 no longer match.
- **Settings moved to JSON:** `Properties.Settings` is now a hand-written class ([Settings.cs](../EliteFIPServer.Core/Properties/Settings.cs)) backed by `%AppData%\EliteFIPServer\settings.json`, with the same property names, so call sites are unchanged. The old `ApplicationSettingsBase` `user.config` lived under `%LocalAppData%\EliteFIPServer\<exe>_Url_<path hash>\<version>\`, so every build and every Store update (new version and new install path) silently reset settings. On first load the new class merges every old `user.config`, oldest first; it is written on the next `Save()` (window bounds are saved on every close). In a Store install, `%AppData%` writes are redirected into the package's private storage, which survives updates. `System.Configuration.ConfigurationManager` was removed with it.
- **Logging fix:** `Log.LogEnabled` was only applied when settings were saved, so NLog wrote `Debug.log` even with Enable logging off. `App` now applies the saved choice at startup.
- **`--start-panel-server`:** a command-line switch that starts the panel server for one run without changing the saved setting. The validation agents launch with it.
